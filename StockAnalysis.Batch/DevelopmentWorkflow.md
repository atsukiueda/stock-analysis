## 1. Purpose and scope

This Procedure defines the controlled workflow for governed development work: intake, upstream knowledge and architecture confirmation, design, implementation handoff, review, validation, release routing, and maintenance feedback. It applies to application, batch, API, automation, infrastructure, and database-integration work within Development Governance scope.

## 2. Principles

Development implements governed knowledge; it does not redefine it. Architecture precedes implementation. Material work remains traceable to applicable upstream authority. Authors do not independently approve their own work. Detailed implementation methods remain delegated.

## 3. Procedure

1. Identify the work purpose, scope, owner, governing authority, and affected downstream consumers.
2. Confirm applicable upstream knowledge, evidence references, and architecture direction; route missing or conflicting authority to the responsible decision role.
3. Establish the governed design context and material change decision route before implementation.
4. Hand off implementation to the authorized development participant under applicable Development Governance controls.
5. Route the resulting work through independent review and applicable validation controls.
6. Preserve traceable relationships among upstream authority, material decisions, validation context, and resulting work product.
7. Route release, withdrawal, rollback, or subsequent change through applicable lifecycle and delivery controls; provide governed feedback upstream where relevant.

## 4. Interfaces and boundaries

This Procedure consumes Knowledge Base, research, architecture, documentation, model, data, and database references where applicable. It does not define code style, branch strategy, API contracts, schemas, build commands, test methods, coverage thresholds, deployment methods, model algorithms, or investment validation.

## 5. Exceptions and delegation

Exceptions follow the authority and conflict route in the Project Constitution. Coding standards, testing mechanics, software review methods, architecture-change methods, build and delivery procedures, and record schemas remain delegated to approved lower-level controls.
